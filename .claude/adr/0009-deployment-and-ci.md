# 0009. Deployment and Continuous Integration

## Context

The app is finished: an ASP.NET Core API that serves the Angular client from the same origin ([ADR 0001](0001-security-and-access-control.md)), backed by SQL Server. It has to run somewhere reviewers can open, and every change should be checked automatically. The roadmap already names Azure App Service and Azure SQL Database.

Several questions are open:

| Open question | Why it matters |
|---|---|
| What does CI check? | The repository has .NET unit and integration tests (Testcontainers), client lint and unit tests, and Playwright tests that need a SQL Server. |
| Which Azure tiers? | It's a test task: cost should be close to zero, but the app must stay reachable while it's reviewed. |
| How does GitHub deploy to Azure? | Deployment needs credentials; they shouldn't be long-lived secrets. |
| When do migrations run? | Development migrates at startup; [ADR 0005](0005-persistence-for-rooms-and-bookings.md) left production to a deployment step. |
| Where do secrets live? | The JWT signing key, the admin account, and the connection string must never be in the repository. |
| Does the app know it's behind a proxy? | App Service terminates TLS, so the app sees plain HTTP from a proxy address, which affects HTTPS redirection and the per-IP rate limits. |

## Decision

### 1. One CI workflow on every push and pull request

GitHub Actions runs three jobs in parallel on `ubuntu-latest`:

| Job | What it runs |
|---|---|
| **.NET** | `dotnet build` (warnings are errors) and `dotnet test`, whose integration tests start SQL Server with Testcontainers on the runner's Docker. |
| **Client** | `npm ci`, `npm run lint`, `npm run format:check`, `npm test`, `npm run build` (bundle budgets apply). |
| **End-to-end** | SQL Server through `docker compose` with a password generated for the run, then Playwright against the published app, exactly as locally. The HTML report is kept as an artifact when it fails. |

### 2. Azure resources: the cheapest tiers that work

All in one resource group in **Poland Central**, the region closest to the venue in Kyiv.

| Resource | Tier | Notes |
|---|---|---|
| App Service plan (Linux) | **F1 Free** | Sleeps after about 20 idle minutes, so the first visit afterwards is slow; 60 CPU minutes a day. Moving to B1 is one setting. |
| Web App | .NET 10 | Serves the API and the client. |
| Azure SQL server + database | **Free offer** (serverless General Purpose) | Pauses when idle; the first query after a pause takes up to a minute, which the EF Core retries from [ADR 0008](0008-fault-tolerance.md) absorb. |

The resources are created by a script in the repository (`infra/provision.sh`, Azure CLI), so the setup is reproducible and reviewable rather than clicked together.

### 3. GitHub deploys with OpenID Connect

A deploy workflow runs after CI succeeds on `master`. It signs in to Azure with **OIDC**: an Entra app registration trusts tokens that GitHub issues for this repository's `master` branch, so no password or publish profile is stored in GitHub. The app registration may only manage this one resource group.

### 4. Migrations run in the deploy workflow, before the new code

The workflow builds an EF Core **migration bundle**, opens the SQL firewall to the runner's IP address for the duration of the step, applies the bundle, and closes the firewall again, even if the step fails. Only then is the new version deployed, so the code never runs against an older schema. The app itself never migrates in production.

### 5. Secrets live in App Service settings

The JWT signing key and the admin password are generated by the provisioning script, and stored only in the Web App's application settings, like the connection string. The SQL administrator password is generated too, and also kept in a GitHub secret for the migration step.

### 6. The app trusts App Service's forwarded headers

`ASPNETCORE_FORWARDEDHEADERS_ENABLED=true` is set, so the app reads the original scheme and client IP from App Service's `X-Forwarded-*` headers. HTTPS redirection and HSTS then work, and rate limits apply per real client rather than to the proxy. The Web App's **HTTPS Only** setting is on as well (ADR 0001).

## Options Considered

| Option | Why not chosen |
|---|---|
| **B1 Basic plan** (about 13 USD a month, Always On) | No cold starts, but a cost for a demo. Kept as the one-line upgrade. |
| **Container Apps or AKS** | More moving parts and cost than a single web app needs. |
| **Publish profile or client secret in GitHub** | Long-lived credentials that can leak; OIDC needs none. |
| **Migrating at app startup in production** | Simple, but every instance races to migrate, and a failed migration takes the site down instead of stopping the deployment. |
| **Managed identity for SQL** | Passwordless and the better long-term choice, but it needs an Entra admin on the SQL server and extra setup; noted as a follow-up. |
| **Bicep or Terraform** | Declarative and idempotent, but a short, commented Azure CLI script is enough for five resources. |

## Consequences

- **Positive:** every push is checked end to end, including concurrency and accessibility; deployments carry no stored Azure credentials; the schema is always migrated before the code that needs it; the hosting costs nothing.
- **Negative:** the free tiers are slow after idling; the SQL firewall is briefly opened to a GitHub runner during each deployment; the SQL admin password is a secret that must be rotated by hand.
- **Follow-ups:** managed identity for SQL, B1 with Always On and App Service's Health check on `/health` if the app needs to stay warm, and Application Insights for logs.
